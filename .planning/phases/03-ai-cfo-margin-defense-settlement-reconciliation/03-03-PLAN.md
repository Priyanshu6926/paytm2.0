  <name>Task 1: Unmatched payments queue retrieval and 1-tap debtor resolution endpoints</name>
  <files>backend/routers/cfo_router.py, tests/test_unmatched_payments.py</files>
  <action>
Extend backend/routers/cfo_router.py with the unmatched payments review queue endpoints per D-04:

1. Implement GET /api/v1/cfo/unmatched-payments:
   - Query unmatched_payments_queue for items with status="PENDING_REVIEW" ordered by created_at DESC.
   - For each queue item, deserialize candidate_customers_json into candidate list.
   - Return list of unmatched payment objects: id, upi_txn_id, amount, payer_name, payer_vpa, candidate_customers, ambiguity_reason, status, and created_at.

2. Implement POST /api/v1/cfo/resolve-unmatched-payment:
   - Define Pydantic request model ResolvePaymentRequest:
     * queue_id: int
     * resolved_customer_id: int
     * merchant_notes: Optional[str] = None
   - Query unmatched_payments_queue for queue_id. Verify status == "PENDING_REVIEW". If not found or already linked, raise HTTP 404 or 400.
   - Verify customer exists in customers table.
   - Execute atomic resolution:
     a. Update unmatched_payments_queue: status="LINKED", resolved_customer_id=resolved_customer_id.
     b. Insert append-only repayment into ledger_entries via deterministic_engine.add_repayment_entry:
        - customer_id=resolved_customer_id
        - amount=queue_item['amount']
        - payment_mode="PAYTM_QR"
        - provider_ref=queue_item['upi_txn_id']
        - source_utterance=f"Manual reconciliation of unmatched payment {queue_item['upi_txn_id']} by merchant"
        - actor="MERCHANT_APPROVED"
     c. Log audit row to business_events:
        - event_category="SETTLEMENT"
        - summary_text=f"Reconciled unmatched QR payment {queue_item['upi_txn_id']} (Rs {queue_item['amount']:,.2f}) to customer #{resolved_customer_id}"
        - evidence_json with queue details and balance after
     d. Commit transaction.
   - Compute new customer balance via calculate_customer_balance.
   - Return response JSON: status="LINKED", queue_id, resolved_customer_id, customer_balance_after, and business_event_id.

3. Create tests/test_unmatched_payments.py:
   - Test GET /api/v1/cfo/unmatched-payments retrieves pre-seeded Suresh Rs 200 queue item.
   - Test POST /api/v1/cfo/resolve-unmatched-payment links payment to Suresh Patil (customer_id=2), clears his Rs 200 udhaar balance down to Rs 0, and updates queue item status to LINKED.
   - Test double resolution of the same queue item is rejected.

<task type="auto">
  <name>Task 2: Paytm QR payment webhook simulation with ambiguity routing</name>
  <files>backend/routers/cfo_router.py, tests/test_unmatched_payments.py</files>
  <action>
Implement simulated Paytm QR payment webhook ingestion in backend/routers/cfo_router.py per D-04:

1. Implement POST /api/v1/cfo/simulate-qr-webhook:
   - Define Pydantic model QRWebhookPayload:
     * upi_txn_id: str
     * amount: float
     * payer_name: str
     * payer_vpa: Optional[str] = None
   - Idempotency guard:
     * Query ledger_entries where provider_ref = upi_txn_id. If exists, return status="ALREADY_PROCESSED".
     * Query unmatched_payments_queue where upi_txn_id = upi_txn_id. If exists, return status="ALREADY_QUEUED".
   - Ambiguity detection logic:
     a. Query customer match using deterministic_engine.resolve_customer_identity(conn, payer_name).
     b. Also search for customers with outstanding udhaar equal to payload.amount.
     c. If status is "NEEDS_DISAMBIGUATION" or multiple customers have outstanding udhaar matching amount:
        - Insert into unmatched_payments_queue:
          upi_txn_id=upi_txn_id, amount=amount, payer_name=payer_name, payer_vpa=payer_vpa,
          candidate_customers_json=json of candidate cards,
          ambiguity_reason=f"Multiple customers matching '{payer_name}' or owing Rs {amount:,.2f}",
          status="PENDING_REVIEW".
        - Log business_events with event_category="CFO_ALERT".
        - Return response JSON: status="QUEUED_FOR_REVIEW", queue_id, ambiguity_reason, and candidate_count.
     d. If exactly one customer match is found with EXACT_MATCH:
        - Auto-reconcile payment: call deterministic_engine.add_repayment_entry(customer_id, amount, payment_mode="PAYTM_QR", provider_ref=upi_txn_id).
        - Log business_events with event_category="SETTLEMENT".
        - Return response JSON: status="AUTO_RECONCILED", customer_id, amount, customer_name, and balance_after.
     e. If no customer match found:
        - Insert into unmatched_payments_queue with ambiguity_reason="Payer name not found in customer records" for merchant manual assignment.
        - Return response JSON: status="QUEUED_FOR_REVIEW", queue_id, ambiguity_reason.

2. Expand tests/test_unmatched_payments.py with tests for:
   - Webhook with payer_name="Ramesh Sharma" (unique single debtor) auto-reconciles payment and updates his ledger balance.
   - Webhook with payer_name="Suresh" and amount=200.0 routes into unmatched_payments_queue with status="QUEUED_FOR_REVIEW".
   - Webhook with unknown customer routes into unmatched_payments_queue for manual merchant assignment.
   - Duplicate upi_txn_id is rejected idempotently.
